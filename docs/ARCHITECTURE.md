# Архитектура

## Стек и почему

| Слой | Выбор | Почему |
|---|---|---|
| Язык | TypeScript (strict) | типы на правилах игры ловят ошибки баланса и событий |
| Сборка | Vite | мгновенный dev-сервер, маленький бандл, PWA без плагинов |
| Тесты | Vitest | тот же конфиг, что у Vite; ядро тестируется без браузера |
| Рендер | Canvas 2D + свой ECS | карточной игре хватает 2D; спрайты кэшируются в offscreen-канвасы, нет зависимости от WebGL-движка, бандл < 150 КБ |
| Интерфейс | DOM-оверлей (без фреймворка) | меню, магазин, подсказки — текст; DOM даёт чёткий шрифт, доступность и CSS-анимации |
| Звук | Web Audio, синтез | вся музыка и эффекты генерируются кодом, ассеты не нужны |
| Графика | процедурная (Canvas paths) | все карты, символы мастей, сигилы Знамений и фон рисуются кодом |
| Мобильные сторы | Capacitor (позже) | тот же веб-бандл |
| Сервер | Node 24 + SQLite, без фреймворка | события аналитики и оплаты Telegram Stars; Node исполняет TypeScript сам |

## Площадки и покупки

Игра знает только интерфейс `Platform` (`src/platform/types.ts`): реклама, `payments`,
облачные сохранения, язык, пауза. Адаптер выбирается при запуске: Яндекс — флагом сборки,
Telegram — по параметрам запуска Mini App, иначе обычный веб.

Покупки: `Payments` даёт `prices()`, `owned()`, `buy()`. Telegram Stars — счёт выставляет
наш сервер (у него токен бота), игра открывает его `WebApp.openInvoice`, оплату подтверждает
бот; Яндекс — SDK площадки. `Entitlements` хранит копию купленного на устройстве и сверяется
с площадкой при запуске и входе в атлас. Каталог (`src/store/catalog.ts`) один на все
площадки, покупка раскрывается в то, что она открывает (набор мецената → атлас → рубашка и
небо). Силу игры не продаёт ничто: только контент «вбок» и внешний вид.

## Внешний вид

Рубашки (`art/cosmetics.ts` + `cardBack` в `art/card.ts`) и темы неба (палитра туманности +
`art/sky-decor.ts`: свои созвездия и живой эффект) выбираются в примерочной атласа и
надеваются, только если куплены (`App.canWear`).

## Ключевой принцип: логика мгновенна, вид — проигрыватель событий

Ядро применяет команду игрока целиком и возвращает **список событий**
(`CardPlaced`, `LineIgnited{breakdown}`, `LinesCleared`, `CardsDrawn`, `NightWon` …).
Презентер берёт события по очереди и превращает каждое в анимацию (`await`).
Отсюда:

- ядро не знает о времени и анимации — тесты быстрые, баланс-симуляция гонит тысячи забегов;
- анимацию можно ускорить или пропустить, не трогая правила;
- сохранение — это просто `JSON.stringify(runState)`.

## Знамения через хуки

`OmenDef` объявляет только нужные хуки: `modifyRules`, `onCardScored`, `onLineScored`,
`onPlacementScored`, `onNightStart`, `onNightEnd`, `onIgnite`. Конвейер подсчёта вызывает
их по порядку слотов (порядок важен — как у джокеров) и пишет каждый вклад в
`ScoreBreakdown.steps`, чтобы презентер показал, какое Знамение что добавило.
Новое Знамение = один объект в `content/omens.ts`, без правки конвейера.

## ECS

Минимальный ECS без внешних зависимостей: сущность — число, компонент — типизированный
токен со своим хранилищем `Map<Entity, T>`, система — функция/объект `update(world, dt)`.
Через ECS живёт всё, что двигается на канвасе: карты, частицы, всплывающие числа, фон.
Игровые правила в ECS **не** живут — для них ECS избыточен, им нужен детерминизм ядра.
